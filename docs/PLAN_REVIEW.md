# PLAN.md v1.0 — Design Review Record

> Pre-build adversarial review of the original build plan (v1.0), performed 2026-08-31, before Phase 0.
> Method: six specialist reviewers (contracts/schemas, Revit API realism, algorithms/MEP/scan, security,
> delivery/CI/effort, product/workflow fit), each finding independently challenged by an adversarial
> verifier (factual claims checked against primary sources — Revit API docs, NEC/IPC, library repos),
> then a completeness critic over the surviving set. 52 review agents in total.
>
> **Result: 44 panel findings survived adversarial verification, 3 notes were accepted unverified,**
> **and the completeness critic added 8 more (55 accepted findings, 6 blockers); 1 finding was refuted and discarded.**
> Every accepted finding is applied in PLAN.md v1.1 — see its `AMENDMENTS (v1.1)` index.

## Overall verdict

The architecture is sound and buildable: allowlisted parameterized ops, signed envelopes, sim-first CI,
bounded solvers, and phase gates are the right skeleton. The findings concentrate on (a) contract gaps that
had to be closed before Phase 0 froze the schemas into three languages, (b) the plugin executor/protocol
semantics, (c) missing inputs for the MEP rules, (d) the absent human-approval surface, and (e) the
one-way-sync assumption (manual Revit edits silently diverging from the scene graph).

## Per-dimension verdicts

### Contracts, JSON Schemas & codegen

The three inline schemas (D1/D2/D3) are syntactically valid draft 2020-12 and the named codegen/canonicalization toolchain is real and feasible in all three languages, so the contracts strategy is sound in outline. However, Phase 0 as written cannot be executed "verbatim": two of the five contract artifacts (wss-messages.v1.json and the per-op args schemas inside ops/registry.json) exist only as prose, the byte-identical round-trip acceptance test conflicts with the schemas' default-materializing generated types, and several semantic holes (footprint meaning, origin/levels optionality, untyped cross-references) will silently propagate into every downstream phase. These need to be fixed in the plan document before Phase 0 starts, not discovered during it.

### Revit plugin & Revit API realism

The Revit-side foundations are sound: Revit 2025/2026 genuinely run add-ins on .NET 8, the Nice3point Revit API NuGet packages are real repackaged Revit assemblies suitable for compile-only CI, mm/304.8 is correct, and the envelope/ExternalEvent/Extensible Storage architecture is the right shape. However, the reference executor in Part G directly contradicts security invariant SI-5 and the per-envelope commit_result protocol, and the seq/id-map persistence story is unimplementable as sketched because Extensible Storage cannot be touched from the network thread. Several op-registry rows (pipe fittings, link_pointcloud/ReCap, active-document binding) compress the hardest Revit realities into one-line API mappings that revit-sim cannot validate, concentrating live-Revit divergence risk exactly where CI is blind.

### Geometry, MEP algorithms & scan pipeline

The MEP math is mostly sound where it is fully specified — E-1's receptacle formula does satisfy the NEC 210.52 max-gap and end-inset bounds, the 81-slide greedy cap is arithmetically correct, and the bounded clash re-plan with REVIEW fallback fails safe. The serious problems are representational and unit-related: rooms exist only as unordered wall-id lists so half the geometric predicates the plan relies on (area, inside-room, circulation, "rooms close") are not computable as specified; two scoring constants (P-1's lambda in FU/m, E-4's +4 penetration penalty) are given in units incompatible with the all-mm coordinate convention and would silently degenerate their optimizations; and P-4 depends on plumbing-datum inputs that no contract carries. Lane B's three-slice classifier provably misclassifies high-sill windows the schema itself permits, and its accuracy gates are measured against synthetic clouds generated from the same model family, so the F1 ≥ 0.95 acceptance overstates field performance.

### Security model & invariants

The security architecture is directionally sound — allowlisted parameterized ops, signed envelopes, atomic commits, and CI-enforced invariants are the right skeleton — but the plan specifies the cryptographic format while omitting the key lifecycle, the trust model it defends against, and the auth story for every surface other than the plugin WSS channel. The taint chain from hostile transcripts is only partially broken: free-string fields (revit_type, revit_family, style_tags) flow from LLM output through validation into signed ops and into a second prompt, and the only mandatory human gate sits at Commit #0, not Commit #1. Two contract-level issues (signature scheme, envelope workstation binding) should be settled before Phase 0 because they are baked into command-envelope.v1.json, which the plan declares immutable-ish source of truth across three languages.

### Phase plan, CI, tooling & effort

The phase decomposition, gate discipline, and CI-without-Revit strategy are fundamentally sound, and the sim-first approach is the right spine for agentic development. However, the plan has one load-bearing hole — every commit and REVIEW flag depends on a human approval surface (Client Portal / HUB) that no phase builds — plus a dependency table that contradicts its own phase descriptions (Phase 6/7), and it defers live-Revit validation of the riskiest ops until effectively the end. Effort estimates are optimistic at the edges (Phase 0's three-language codegen plus byte-identical canonical JSON is not a 2–3 day task) but the ~11-week serial total is roughly plausible if the approval-surface and catalog workstreams are added explicitly rather than discovered mid-phase.

### Product & workflow fit

The plan is a well-engineered one-shot generation pipeline, but it models a demo, not Chapter's design workflow: it assumes the Revit model is never touched by a human between Commit #0 and the spec PDF, offers no revision path once a client reacts to renders, and defers every human approval surface it depends on to a UI no phase builds. The layout schema also stops at walls/doors/furniture, so the client-facing deliverables the plan itself promises (interior renders, a CSI spec with Division 09 finishes) have no data source for finishes, casework, or fixture semantics. Most of these are fixable cheaply now because contracts are Phase 0 deliverables frozen thereafter; several become expensive re-architecture if discovered in Phase 6-8.

### `algorithms-1` — blocker · design_gap · verified

**Claim.** Rooms are defined only by an unordered boundary_wall_ids list (D1) with no polygon or derived-area representation, and the plan never specifies how room geometry is derived from wall centerlines; consequently Phase 4's "deterministic" validator checks ("rooms close", "circulation ≥ circulation_min"), Phase 5's inside-the-room and circulation predicates, and Part G's room-facing normal n̂ (needed by P-2 fixture snap and back-to-wall placement) are underdetermined as specified — a wall can bound multiple rooms along different sub-segments, no wall-endpoint meeting convention is given, and centerline vs. finished-face ambiguity changes computed area by the wall thickness (generated walls carry no thickness, only revit_type) — and "circulation" has no operational definition anywhere in the plan. This must be resolved before Phase 0 freezes the schema, since later contract changes are human-gated and force full regeneration. (Note: Phase 6 P-1's wet-room wall adjacency is directly computable from boundary_wall_ids and is not affected.)

**Evidence.** D1 rooms schema stores only boundary_wall_ids (minItems 3, unordered, no polygon/area field; min_area_m2 is optional input, not derived). Yet Phase 4's validator must check 'rooms close' and 'circulation >= circulation_min', Phase 5's greedy needs 'inside the room' and circulation predicates, and Phase 6 P-1 needs 'walls with >= 1 adjacent wet room'. A wall centerline can bound multiple rooms along different sub-segments, walls need not meet at shared endpoints, and centerline vs. finished-face ambiguity changes computed area by the wall thickness — polygonization from this representation is underdetermined, and 'circulation' has no operational definition (clear-width erosion? path width between AABBs?).

**Change applied (v1.1).** Before Phase 0 freezes the schema, add an ordered `boundary` polygon (array of pt2, derived+validated against boundary_wall_ids) to the room object, or specify a deterministic polygonization algorithm (e.g., shapely polygonize over noded wall centerlines, room = containing face) plus the wall-endpoint meeting convention; separately define the circulation check operationally (e.g., free-space polygon eroded by circulation_min/2 must keep all door thresholds in one connected component).

### `contracts-1` — blocker · design_gap · verified

**Claim.** ops/registry.json is a Phase 0 deliverable sourced "verbatim from Part D" (line 466) and described as "Part D4 as machine-readable data" (Part C line 65), but D4 is an informal prose table and D3's envelope schema types ops[].args as a free-form object with no per-op constraint. Although line 443 implies per-op "JSON args schema" artifacts exist (for future op additions), the plan never specifies the registry file format, the args schemas for the 15 initial ops, or which components (gateway, sim, plugin) validate args against them — so SI-2's "schema-valid args" requirement is not machine-checkable as specified, and no acceptance item tests a known op with schema-invalid args.

**Evidence.** D3 command-envelope (line ~404-411) defines ops items as {op: string, args: object} with no per-op constraint; Part C line 65 says registry.json is 'Part D4 as machine-readable data'; D4 arg cells like 'flags{}' and 'path[[x,y,z]...]' are informal prose. SI-2 (Part F) and Phase 1 acceptance ('envelope with unknown op rejected') require the gateway, sim, and plugin to all validate args against something that is never specified. Phase 0 acceptance (line 466-471) requires this file to exist and verify.

**Change applied (v1.1).** Specify the registry.json format in Part D now: one entry per op with an embedded full JSON Schema 2020-12 for its args (e.g. {"op":"create_wall","args_schema":{...},"revit_mapping":...}), including the pt2/pt3 $defs, and state that gateway (before signing), sim, and plugin (before enqueue) all validate every ops[i].args against args_schema; add a Phase 0/1 acceptance item 'op with schema-invalid args → whole envelope rejected'.

### `product-1` — blocker · design_gap · verified

**Claim.** The plan has no mechanism to detect or reconcile manual designer edits to the Revit model, yet every agent after Commit #1 plans from a frozen Postgres scene-graph snapshot. All four model-read ops in D4 (export_views, export_parameters, verify_deviation, run_interference_check) serve renders, specs, scan QA, and clash checks — none refreshes the scene graph or id_map, and the wss-messages contract has no slot for model-originated change events. A wall nudged between commits either triggers Phase B rollbacks the orchestrator cannot explain (it re-plans from the same stale snapshot) or diverges silently — offset-hosted doors/windows/devices shift with their moved host wall, and deleted elements leave dangling ElementIds in the id_map with no defined recovery for later set_parameter/set_phase_demolished ops. Fix before Phase 0 codegen locks the contract set into three languages (amendment is possible later but touches every layer): add a drift-check primitive (verify_model_state returning existence + geometry hash per id_map element) with a gateway gate that routes mismatches to REVIEW and a defined resync path — or explicitly state a model-lock-between-commits workflow policy and acknowledge it as a business constraint on designers.

**Evidence.** Part B pipeline and D3 define a strictly one-way flow: cloud scene graph → signed envelopes → plugin; the only model-read paths are export_views/export_parameters (D4), used for renders and specs, never to refresh the scene graph or id_map. Phase 4 freezes the snapshot; Phases 5-6 compute placements, receptacle runs (E-1), and clash Phase A against that frozen copy, while Phase B interference runs against the real (possibly hand-edited) model — producing rollbacks the orchestrator cannot explain or fix. Nothing in Parts D-J mentions Revit's DocumentChanged event, a state-hash, drift detection, or resync; the wss-messages and op registry (Phase 0 contract deliverables) have no slot for it.

**Change applied (v1.1).** Before Phase 0 freezes contracts, add a drift-check primitive: a `verify_model_state` (or extended export_parameters) op returning existence + geometry hash for every id_map element, a gateway gate that runs it before building any envelope and routes mismatches to REVIEW with a defined resync path (re-import changed elements into the scene graph, or explicit human 'accept model as truth' that rebases the snapshot). Alternatively, state an explicit workflow policy that the model is locked between commits — and acknowledge in the plan that this is a business constraint designers must accept.

### `revit-1` — blocker · design_gap · verified

**Claim.** The reference EnvelopeHandler in Part G (marked 'implement exactly') drains the entire queue inside one TransactionGroup, so queued envelopes commit or roll back together — contradicting the envelope-granular TG implied by SI-5, the per-envelope commit_result{envelope_id, committed|rolled_back, id_map_delta} in D3, and Phase 6's whole-TG rollback on hard interference (which presumes TG = the Commit #2 envelope). The same drain-in-one-TG design is repeated in Phase 1's build text (plugin executor bullet), and Phase 1's single-envelope E2E would not catch it. Additionally, because ExternalEvent.Raise is coalesced while pending, an exception mid-drain leaves remaining queued envelopes unprocessed until a later Enqueue raises the event again.

**Evidence.** Part G 'Plugin executor core': Execute() opens `new TransactionGroup(doc, "HUB Batch")` then `while (_q.TryDequeue(out var env))` — N queued envelopes share one TG; the single catch rolls back all of them and Report(ex) cannot attribute a commit_result{envelope_id, committed|rolled_back} per envelope (D3 WSS message set). SI-5 says 'Every envelope executes atomically'. Also, if RunBatch throws mid-drain, envelopes still in the queue lose their consumed ExternalEvent Raise and stall until the next enqueue.

**Change applied (v1.1).** Rewrite the reference sketch before Phase 1: one envelope per Execute pass — dequeue exactly one, open its own TransactionGroup, Assimilate or RollBack, send its commit_result with id_map_delta, then re-Raise the event if the queue is non-empty. State explicitly in Part G that the TG boundary equals the envelope boundary.

### `revit-2` — blocker · design_gap · verified

**Claim.** The plan requires the plugin to verify strictly-increasing seq "before enqueue" (D3), and Part C/Part G place that verification on the background WSS thread — where no Revit API access is legal (Extensible Storage reads/writes require a valid API context; writes require a Transaction), so the check can only use in-memory state. The plan never says where last-accepted seq is persisted, whether it survives plugin/Revit restart, or whether a rolled-back envelope consumes its seq (forcing the gateway to re-issue under a fresh seq — unspecified). After a restart the in-memory counter resets, reopening a TTL-bounded (up to 3600s) replay/duplicate-execution window: a gateway retransmit within TTL would re-execute already-committed envelopes on the live model, contradicting SI-3 and Phase 10's "plugin idempotent via seq" chaos test (which only covers gateway restart). Fix: check HMAC+TTL on the network thread; check seq at Execute time against a last-committed seq persisted in Extensible Storage within the envelope's TransactionGroup (hydrated into memory at document-open), and add the last-committed seq to the hello message so the gateway resumes from the model's truth.

**Evidence.** Part G: `Enqueue(e) { if (Verify(e)) ... }` is called from the background WSS client (Part C src/Transport); D3 says the plugin verifies 'sig, TTL, and strictly increasing seq' before enqueue; Part C/Phase 1 say id-map (and by implication plugin state) persists via Extensible Storage. Nothing says where last-accepted seq is stored, whether it survives restart, or whether a rolled-back envelope consumes its seq (if it does, the gateway can never retry; if it doesn't, the enqueue-time check is wrong).

**Change applied (v1.1).** Split verification in the plan text: HMAC + TTL checked on the network thread; seq checked at Execute time on the API thread against a last-COMMITTED seq persisted in Extensible Storage inside the same TransactionGroup as the ops (so rollback releases the seq and the gateway may re-issue). Document restart recovery: on document open, read last-committed seq from ES and send it in the `hello` message so the gateway resumes from the model's truth.

### `algorithms-2` — major · factual_error · verified

**Claim.** The Lane B slice-classification table (Part G) classifies any window whose sill is at or above ~1200 mm (the z0+1200 slice) as solid wall, even though the D1 schema allows sill_height up to 1800 mm — so schema-legal high-sill windows (common in prewar kitchens/baths) are silently dropped, with no confidence flag and no deviation-gate catch, and Phase 9's F1 >= 0.95 gate can only pass if the synthetic fixture set avoids the legal sill range. Several occupancy patterns (e.g. gap only at the top slice: transoms; tall doors under ceilings below ~2590 mm) map to no table row at all, and the all-gap "cased opening" row carries no gap-width or collinearity/co-thickness rule to distinguish a cased opening from two unrelated collinear walls. fixtures-gen includes furniture clutter blobs but nothing inside opening gaps (e.g. open door leaves), which would flip rows in real captures.

**Evidence.** Slices are fixed at z0+150, z0+1200, zc-150. A window with sill 1200-1800 mm (permitted by D1 windows.sill_height max 1800 — e.g., high kitchen/bath windows common in prewar units) is occupied at all three heights → row 1 'solid wall', so Phase 9's 'F1 >= 0.95 doors vs windows vs solid' gate is structurally unreachable on schema-legal inputs. The all-gap row also carries no rule for distinguishing a cased opening from two unrelated collinear walls, and real captures add occupancy in gaps (open door leafs at z0+1200) and under windows (radiators at z0+150), flipping rows.

**Change applied (v1.1).** Replace the three fixed slices with a per-candidate-gap vertical occupancy profile (e.g., 100 mm z-bins over the full wall height) classified by sill/header extraction from the profile; define cased openings explicitly as bounded gaps between collinear co-thickness wall segments (gap width <= ~2500 mm); add open-door-leaf and radiator artifacts to fixtures-gen so the F1 gate exercises these failure modes.

### `algorithms-3` — major · risk · verified

**Claim.** Phase 9's only accuracy evidence (centerline 15 mm, thickness 10 mm, F1 >= 0.95) is measured exclusively on fixtures-gen clouds synthesized from the same golden layouts using straight, constant-thickness planar walls plus i.i.d. Gaussian noise — the same hypothesis class the RANSAC slice/line extractor fits. The generator does include furniture clutter, a mirror-dropout region, and a uniform 0.7% scale-drift test, but not low-frequency registration warp, wall-hugging geometry (baseboards, radiators, pipes), or partial glass returns, and no phase in the plan validates Lane B against a real Polycam capture; so the gate establishes self-consistency rather than expected real-world accuracy, and the production RMS>20 mm deviation gate is likely to fire far more often on real captures than the synthetic numbers suggest, adding load to the already-mandatory human review of Commit #0.

**Evidence.** Phase 9 Build: fixtures-gen 'synthesize ground-truth point clouds from golden layouts (sample wall faces + Gaussian noise sigma=8 mm + furniture clutter + mirror dropout)'. The generator emits exactly straight, constant-thickness walls with i.i.d. Gaussian noise — the same hypothesis class RANSAC-line extraction fits — while real iPhone-LiDAR/Polycam clouds exhibit registration drift (low-frequency warp, not Gaussian), baseboards/crown/pipes hugging walls, and partial glass returns; none are generated, so the 15 mm/0.95 numbers will not transfer and the RMS>20mm deviation gate will fire constantly in production.

**Change applied (v1.1).** Add to Phase 9 acceptance one real Polycam capture of a known unit (measured by tape) as a non-CI, human-verified artifact with its own looser tolerance; extend fixtures-gen with low-frequency registration warp (e.g., 1-3 cm sinusoidal drift), baseboard/radiator strips, and partial-return glass, and report accuracy separately per artifact class.

### `algorithms-5` — major · design_gap · verified

**Claim.** P-4 branch feasibility and its Phase 6 acceptance test require h_plenum, pipe diameter, and h_fitting, but no contract schema, config, or catalog in the plan declares any of these (D1 meta.levels has only floor_z/ceiling_z; fixtures carry no drain diameter; the only catalog is products.json SKU data), so the formula is uncomputable from declared inputs despite Part G's 'implement exactly' mandate. L's metric is also undefined — for fixtures snapped to the selected wet wall it is the along-wall offset to the stack, but for wet rooms not adjacent to that wall the routed length exceeds straight-line distance and must be specified. Additionally, the fixed 2.08% slope is required only for pipes under 3 in under IPC-based codes (including NYC's Table 704.1), which permit 1/8 in/ft for 3–6 in pipe (UPC allows 1/8 in/ft only at 4 in+ with AHJ approval), so hardcoding 0.0208 halves L_max for the 3-in WC branch and will over-trigger the second-stack path in Chapter's IPC/NSPC jurisdictions; the slope should be a size-dependent, configurable value.

**Evidence.** Part G P-4 and the Phase 6 acceptance test both use L_max = (h_plenum - dia - h_fit)/0.0208, yet D1's meta.levels has only floor_z/ceiling_z (no slab/plenum depth), fixtures carry no drain diameter, and no catalogs entry supplies fitting heights — the formula is dimensionally fine (0.0208 unitless, all mm) but uncomputable from declared inputs. ## Open decisions for Eran

These do not block Phase 0; each blocks the phase noted.

1. **Ed25519 vs per-project HMAC** (blocks Phase 1). The v1.1 wire format `{payload, sig}` is
   signature-scheme agnostic. HMAC (specified lifecycle: HKDF per project, enrollment delivery, DPAPI,
   rotation runbook) is simpler; Ed25519 removes workstation key secrecy entirely — a workstation
   compromise can then never forge envelopes for other workstations. Recommendation: Ed25519.
2. **Review-card UI surface** (blocks Phase 2 usability). Render approvals in the existing HUB UI
   (itemize that integration) or build a minimal internal page on the gateway. The Phase 1 approvals
   REST API supports either.
3. **Catalog contents** (block Phases 2/4/8). As-built wall type names + thicknesses from Chapter's
   Revit template; the new-construction wall/door/window type vocabulary; the 30 real product SKUs.
   Placeholders exist and are marked — they will not resolve on the live template.
4. **Multi-level support** (future schema version). v2.3 is single-level by explicit constraint;
   duplex/triplex projects need levels[] + per-element level refs + a stair entity.
5. **Floor/ceiling finish modeling** (Phase 8 scope). v1 marks floor/ceiling finishes 'BY SEPARATE
   SCHEDULE'; modeling them needs create_floor/create_ceiling ops + per-room finishes in the schema.
